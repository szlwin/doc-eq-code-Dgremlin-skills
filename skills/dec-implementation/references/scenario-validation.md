# 框架与业务场景验证

按本次实现风险选择测试；不要为满足列表而虚构设计规则。所有并发、幂等、重试和副作用结论都应说明具体契约及未覆盖边界。

| 场景 | 验证重点 |
|---|---|
| 同聚合并发命令 | 用独立线程、真实事务和屏障制造竞争；检查最终数据库行、调用次数及失败请求，不只断言无异常。并发策略来自锁、约束和事务，不能用 synchronized 掩盖问题。 |
| 重复、乱序回调 | 按当前设计验证拒绝或幂等语义及副作用次数。没有请求/事件/支付尝试 ID 时，不声称能识别跨尝试迟到消息，也不擅自加入新业务协议。 |
| 一对多关系 | 准备至少两条不同主键的明细，按设计外键读完整集合；验证 every/any、全部回写、回滚和其他聚合隔离。不得以 get(0) 或主键等于父主键实现集合关系。 |
| 自定义 Action 失败 | 在前序持久化动作之后注入失败，检查事务回滚、模型未发布及提交后回调未触发。外部与 Runtime 自管模式分别验证。 |
| 截止时间 | 使用可控时钟覆盖执行前、最后一个 Action 返回后、最终写回后到期。验证 TIMEOUT 和真实回滚；不把同步检查描述成能抢占阻塞线程。客户端仍必须设置 I/O 超时。 |
| 提交后发送失败 | 断言数据库已经提交，并明确重试是否会再次发送。不能宣称外部副作用与数据库天然原子，可靠投递按独立契约实现。 |
| 设计演进 | 修改 Information 条件或 Directory 边，重新生成并编译投影，用同一应用接线验证行为变化，同时验证旧设计实例不受影响。 |
| 第二领域 | 用不同实体和状态含义的小场景复用相同 Runtime；验证设计、生成产物和实际执行，不靠复制订单专用分支。 |
