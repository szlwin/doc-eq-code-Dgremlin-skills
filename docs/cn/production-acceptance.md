# 从 Demo 到生产的验收清单

[English](../en/production-acceptance.md)

本清单是生产化的待验收契约，**不表示这些能力已经实现或验证**。订单 Demo 的支付平台、MongoDB 和短信仍是本地替身；Back 后迟到回调、短信 afterCommit 缺少重试等边界已在 Demo 文档中说明。框架测试、Binding VERIFIED 和本清单均不能单独证明生产就绪。

每一项需在目标环境登记负责人、设计 revision、实现/迁移版本、可复现测试命令、报告地址和验收结论；未满足的项保留 BLOCKED 或待验收状态。是否接受残余风险由实际业务负责人决定。

| 验收项 | 必须形成的设计/实现决策 | 可复现的验收证据 |
|---|---|---|
| 支付尝试身份 | 独立 `paymentAttemptId`，与订单、平台单号和本次尝试关联；明确重新支付、Back 与尝试失效规则 | 同一订单两次尝试交错回调，旧尝试不能覆盖新尝试；保留原始事件和处置原因 |
| 回调去重 | `callbackId` 或平台事件唯一键、唯一约束、验签、重放窗口；明确重复成功、失败后成功及乱序策略 | 重复、并发、乱序、伪造、过期回调的契约测试；幂等命中后不重复扣款/通知 |
| 迟到事件 | 按尝试/业务版本识别迟到，明确拒绝、忽略、补偿或转人工规则；禁止靠当前状态猜测历史 | Back 后迟到成功、跨尝试失败、服务重启后重放测试；账务及审计结果一致 |
| 可靠投递 | Outbox 或等效机制，把业务提交与待发送事件可靠关联；重试、去重、死信、人工重放及告警 | 提交后进程崩溃、发送成功但确认丢失、通知服务长时间离线；恢复后不丢事件、重复可控。afterCommit 回调本身不足以满足该项 |
| 真实适配器 | 支付、MongoDB、短信的真实超时、限流、错误码、幂等键、鉴权和事务能力；禁止静默退回内存实现 | 对真实沙箱/契约服务执行成功、超时、断连、限流、部分成功测试，验证业务冲突与基础设施错误分类 |
| 数据库迁移 | 明确版本化迁移、唯一约束、索引、数据回填、兼容窗口和回滚/前滚策略 | 从上一版本数据升级；重复执行安全；中断恢复；旧/新应用兼容性及备份恢复演练 |
| 并发与负载 | 由业务给出吞吐、并发、P95/P99 延迟、错误率及资源预算；锁/隔离/重试策略明确 | 在目标规模数据上验证重复提交、热点订单、死锁、池耗尽、查询分页与候选集上限；保留测量环境和原始报告，不预填虚构指标 |
| 可观测与审计 | 贯通订单/尝试/回调/通知 ID，审计追加记录、隐私保护、权限控制、追踪与告警 | 可重建事件顺序与处置原因；当前事实查询不能替代历史审计；验证越权及敏感字段脱敏 |
| 发布与回退 | 设计、XML、受管 Java、应用 JAR、配置和 Binding 证据属于同一 revision | CI 可重建，无派生产物漂移；`--require-ready` 通过且报告来源可信；灰度、回退及故障演练有记录 |

建议先确定支付尝试与事件身份，再设计一致性及可靠投递；然后替换适配器、执行迁移和负载验证。新增业务规则应先进入 canonical YAML；当前语言或 Runtime 无法表达的部分应明确记录 DESIGN_GAP/能力缺口及责任边界，不能隐藏在适配器里。
