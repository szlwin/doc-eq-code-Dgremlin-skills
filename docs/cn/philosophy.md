# 项目理念：让设计参与程序运行

[返回文档总览](README.md)

做过业务系统的人，大概都遇到过这样的情况：需求文档说订单可以支付，代码里却还有几个没写出来的限制；流程图已经改了，某个接口仍按旧规则执行。等到出了问题，大家才开始追问：现在到底以哪一份为准？

这些差异往往来自同一条规则被写了好几遍。文档写一次，接口判断一次，后台任务再判断一次。每一份单独看都合理，改需求时却很容易漏掉其中一处。

DEC 想减少这种重复。把数据、判断条件和业务流程放进一份结构化设计，让人能读懂，也让程序能使用它。规则变了，先改这份设计，再更新受影响的页面、代码和测试。仓库里的订单支付 Demo，就是对这种做法的一次尝试。

## 从一笔订单说起

先看 [订单支付流程图](../../demo/design-html/directory/order-payment.html)。它描述了一条常见的业务路径：提交订单，发起支付，收到支付结果，再分别处理成功和失败。

这里真正需要说清楚的，往往是箭头之间的条件。什么样的订单允许支付？用户是否有效？收到失败结果以后，要记录什么，要不要通知用户？这些约定决定了程序应该怎么做。

在 Demo 的 [流程设计](../../demo/order-payment-yaml/business-order-payment.yaml) 中，进入“支付中”之前，要检查“订单可支付”和“用户有效”。收到支付结果后，由成功或失败条件选择分支；失败分支安排错误记录、短信通知和订单状态更新。

这些内容写在 YAML 里。YAML 是一种文本格式，在这里用来保存正式设计；文档中提到的 canonical YAML，就是这份作为修改依据的设计源。生成的 HTML 把它画成流程图，方便人审阅。应用运行时，共享执行引擎会读取设计，检查条件、选择分支并调用相应动作。这个引擎在项目里称为 Runtime。

因此，流程图上的分支与程序执行的分支可以追溯到同一处定义。接手的人看到“支付失败后发送通知”，能继续找到它对应的动作和实现，不必再猜图和代码是否说的是同一件事。

## 把“是什么”和“怎么做”分开

理解这个 Demo，可以先从两个问题入手：**这笔订单现在是什么情况？接下来允许做什么？**

“用户有效”“订单可支付”“支付结果为失败”，都是对当前数据的判断。DEC 用 Information 表达这样的业务事实。同一个事实可以被多个地方引用，例如进入支付流程前要判断订单是否可支付，另一个业务入口也可以使用同一个判断。

“检查条件后发起支付”“收到失败结果后记录错误”，则是在安排事情怎样发生。DEC 用 Directory 组织这些流程阶段，把判断条件和要执行的动作连起来。

其余几个名称，也可以放回这个例子里理解：

| 设计中的名称 | 在订单 Demo 里做什么 |
| --- | --- |
| Data / View | 描述订单、明细、用户、支付信息，以及一次业务处理需要把哪些数据放在一起 |
| Information | 表达“订单可支付”“用户有效”等当前是否成立的事实 |
| RuleView | 组织具体的检查、读取或写入规则，供事实判断或流程动作使用 |
| Directory | 描述流程怎样推进，何时执行动作，怎样选择分支或回退 |
| API | 约定外部怎样提交订单、发起支付、传入结果和查询数据 |

这种拆分的用处，是让一个判断有明确的归属。以后调整“订单可支付”的条件，应能找到它的定义和引用，而不用去每个接口里搜索相似的 `if`。查询也能使用设计中的事实来识别订单当前处于哪个阶段。各个概念的完整说明见 [设计模型](design-model.md)。

不过，“现在是什么情况”不能回答所有问题。Demo 可以查询当前支付成功的订单，但仅凭当前数据，不能回答“这笔订单上周是否支付成功过”。回退操作会改变当前数据，却不会抹去已经发生的事情。要查历史、做审计，仍然需要单独保存事件或业务记录。

## 改一条规则时，要改哪些地方

假设以后增加一项要求：发起支付前，必须检查订单是否超过支付期限。这是一个扩展示例，当前 Demo 并未实现这项功能。

我们首先要把“是否超时”定义清楚：从什么时候开始计时，使用什么时间字段，超时后还能不能重新下单。然后在设计中补上判断，并让发起支付的流程引用它。若现有规则能力无法完成这项检查，还需要补充实现。

设计修改后，重新生成阅读页面和受影响的代码，再验证期限内、期限外以及边界时刻的行为。这样可以沿着同一条线检查：设计里有没有这个要求，流程有没有使用它，实现是否支持，测试是否覆盖。

这也是“一份设计，多处使用”的实际含义。HTML 帮人看懂设计，生成代码提供类型和接入接口，Runtime 按设计执行。它们各有用途，但业务条件应从同一个地方修改。只改页面上的文字，或者只在某个接口里加判断，都会让这条联系断开。

有时外部工具会修改 XML，这些改动也可以 [受控地合并回 YAML](xml-to-yaml-sync.md)。合并完成后，后续产物仍从 YAML 生成，避免两边各自演进。转换和生成的具体关系见 [YAML、XML 与 HTML](yaml-xml-html.md)。

## 设计写清楚了，代码还要做什么

以失败通知为例，设计可以说“支付失败后执行短信通知”，但怎样连接短信平台、怎样处理超时、发送失败要不要重试，都需要工程实现。

Demo 为这件事提供了一个具体例子：短信动作先登记提交后的回调，数据库事务成功提交后才调用发送器。目前的发送器只打印日志。这个例子能说明通知与事务的执行顺序，却不能证明一条短信真的送到了用户手机。

同样，设计里有“记录支付错误”，不意味着已经接好了生产环境的 MongoDB；流程图里有“发起支付”，也不意味着已经接好了真实支付平台。Demo 的这些外部能力使用本地替身，详见 [订单支付示例](order-payment-demo.md)。

业务设计与工程实现需要在这里接上：设计说明什么时候做、需要得到什么结果；代码负责访问真实资源、管理事务并处理故障。设计没有说明的行为，要补充约定；实现暂时做不到的能力，要留下明确的缺口。遇到缺失适配器、无法判断的条件或执行错误，最可靠的做法是明确报告失败或登记缺口，而不是继续往下走并把结果说成成功。比如支付结果无法识别时，不能默认当成支付成功；一个分支还没有接通时，也应保持未完成状态。项目里的 `DESIGN_GAP`、`UNRESOLVED` 和 `ERROR` 都是在提醒接手者：这里还不能作出确定结论。

## 把这份约定交给下一个人

我们把这样的设计称为“可执行的业务契约”，是因为它既帮助双方说清楚约定，也能参与实际检查和执行。

负责设计的人，需要把条件、流程和输入输出写清楚，让每个需要追踪的节点有稳定的 Design ID。负责实现的人，需要找到这些节点对应的代码或运行时能力，并用测试说明它们确实按约定工作。项目里的 Implementation Binding，就是记录这些对应关系的清单。

例如，“支付失败后应更新订单状态”不能因为设计里写了、代码也生成了，就算完成。还要真的让一笔订单走过失败路径，检查状态是否正确；如果中途写入失败，也要检查有没有留下不完整的数据。已有的并发测试还会让两个请求同时提交同一订单，核对接口返回和最终数据库内容。这些测试方法见 [开发与验证手册](development-and-verification.md)。

有了这层对应关系，接手的人就可以从业务节点找到实现和测试。由 Agent 参与开发时，也使用同一份约定：已实现的要有依据，没做完的继续标明未完成。设计或代码变了，就重新核对受影响的测试，不能一直拿上一次通过的报告作为保证。

测试和自动检查能减少遗漏，但业务要求本身是否合理、场景是否考虑充分，仍需要人来判断。这份契约的价值，是让讨论有具体的落点。

## 什么时候值得这样做

这种做法需要前期投入。原来可以直接写进代码的判断，现在要先想清楚它属于数据、事实还是流程；团队也需要学习模型和工具。规则变化时，要一起维护设计、适配代码和测试。

应用还会依赖 Runtime 的执行方式和生成器的能力。遇到表达不了的需求，可能要扩展框架或编写适配器。支付、消息、数据库之间的一致性，以及重试、补偿和历史记录，也都需要另外设计。采用 DEC 并不会省掉这些工作。

如果业务要维护很多年，同一条规则经常被多个入口使用，或者项目需要反复交接，这些投入比较容易带来回报：少维护几份重复判断，改动时更容易知道影响了哪里，接手时也有一条从设计走到实现和测试的路径。

如果只是一个短期使用、规则很少的小工具，直接写清楚代码并配好测试，可能更省事。是否采用 DEC，可以从项目眼前的问题判断：团队是否已经花了很多时间核对文档与代码，是否经常因为同一规则有多份实现而出错。

想继续了解，可以先打开 [订单支付 Demo](order-payment-demo.md)，对着流程图走一遍成功、失败和回退路径；再看 [整体架构](architecture.md)，了解设计怎样被程序读取和执行。

## 接下来会遇到的几个词

| 词 | 在项目里可以怎样理解 |
| --- | --- |
| canonical YAML | 作为修改依据的那份设计源，XML 和 HTML 都从它派生 |
| Runtime | 读取设计、判断条件、推进流程的共享执行引擎 |
| Design ID | 设计节点的稳定身份，帮助代码、测试和文档指向同一个节点 |
| Binding | 记录某个设计节点由什么代码、Runtime 能力或测试负责实现 |
| DESIGN_GAP | 设计或实现中还存在的明确缺口，不能悄悄当成已完成 |
