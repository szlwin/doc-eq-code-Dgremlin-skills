# Acceptance checklist: from demo to production

[中文版](../cn/production-acceptance.md)

This checklist defines acceptance requirements for production use. **It does not mean these capabilities have been implemented or verified.** The order-payment demo still uses local substitutes for the payment platform, MongoDB, and SMS. Its documented limitations include late callbacks after Back and the lack of retry guarantees for SMS sent through afterCommit. Framework tests, VERIFIED Bindings, and this checklist cannot individually establish production readiness.

For each item, record the owner, design revision, implementation and migration versions, reproducible test commands, report location, and acceptance decision in the target environment. Unmet items remain BLOCKED or pending acceptance. The responsible business owner decides whether to accept any residual risk.

| Acceptance item | Required design and implementation decisions | Reproducible acceptance evidence |
|---|---|---|
| Payment attempt identity | Use a distinct `paymentAttemptId` linked to the order, provider transaction number, and current attempt. Define how retries, Back, and attempt invalidation work. | Interleave callbacks from two attempts for the same order. An old attempt must not overwrite the new one. Preserve the original events and reasons for their disposition. |
| Callback deduplication | Define a `callbackId` or unique provider event key, uniqueness constraints, signature verification, and a replay window. Specify how duplicate successes, success after failure, and out-of-order events are handled. | Contract tests for duplicate, concurrent, out-of-order, forged, and expired callbacks. An idempotent repeat must not charge or notify again. |
| Late events | Identify late events by attempt or business version. Explicitly choose rejection, ignoring, compensation, or manual review; do not infer history from current state alone. | Test a late success after Back, a failure from a different attempt, and replay after restart. Accounting and audit results must remain consistent. |
| Reliable delivery | Use an Outbox or equivalent mechanism to durably associate business commits with pending events. Define retries, deduplication, dead letters, manual replay, and alerts. | Simulate a crash after commit, delivery with a lost acknowledgment, and a prolonged notification outage. Recovery must avoid event loss and control duplicates. An afterCommit callback alone is insufficient. |
| Real adapters | Define actual payment, MongoDB, and SMS behavior for timeouts, rate limits, error codes, idempotency keys, authentication, and transactions. Do not silently fall back to an in-memory implementation. | Run success, timeout, disconnection, rate-limit, and partial-success tests against real sandboxes or contract services. Verify the distinction between business conflicts and infrastructure failures. |
| Database migrations | Define versioned migrations, uniqueness constraints, indexes, backfills, compatibility windows, and rollback or roll-forward strategies. | Upgrade from the previous version's data. Verify safe repeated execution, recovery from interruption, old/new application compatibility, and backup restoration. |
| Concurrency and load | Have the business specify throughput, concurrency, P95/P99 latency, error-rate, and resource budgets. Define locking, isolation, and retry policies. | Test duplicate submissions, hot orders, deadlocks, pool exhaustion, query pagination, and candidate limits using data at the target scale. Preserve the environment description and raw reports; do not invent target measurements. |
| Observability and audit | Correlate order, attempt, callback, and notification IDs. Define append-only audit records, privacy protection, authorization, tracing, and alerts. | Reconstruct event ordering and the reasons for each action. Current-fact queries cannot replace historical audit. Verify access controls and masking of sensitive fields. |
| Release and rollback | Keep the design, XML, managed Java files, application JAR, configuration, and Binding evidence on the same revision. | CI can reproduce the artifacts without drift. `--require-ready` passes and test report provenance is trusted. Record staged rollout, rollback, and failure-recovery exercises. |

Start by defining payment attempt and event identity, then consistency and reliable delivery. Follow with real adapters, migrations, and load verification. New business rules must first enter canonical YAML. Where the language or Runtime cannot express a requirement, record the DESIGN_GAP or capability gap and the responsible boundary explicitly; do not hide it inside an adapter.
