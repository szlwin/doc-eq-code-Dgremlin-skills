# 项目理念：让设计成为可执行的业务契约

[返回文档总览](README.md)

## 1. 要解决的问题

传统项目常在需求文档、流程图、接口、Service、数据库状态值和测试中多次描述同一件事。例如“订单具备支付条件”可能同时出现在流程图的箭头说明、Java 的 `if` 条件和 SQL 的状态列表中。任何一处变更，都可能导致其余位置滞后。

本项目将这类业务事实放入 canonical DEC YAML：由 Information 描述事实如何成立，由 Directory 描述流程如何推进，由 RuleView/Action 描述执行，由 Data/View 描述数据及关系。XML、HTML 和 Java 导航代码从这份设计派生，实际行为由共享 Runtime 解释执行。

“文档即编码”在这里意味着**结构化设计参与程序执行和验证**。它不意味着任意自然语言文档都能自动运行，也不意味着生成器已经实现数据库、短信和支付平台的全部集成。

## 2. 一份业务事实，多个可追踪的表现形式

以订单支付为例：

- `order.payable` 表示订单是否满足支付条件。
- `common.ordered` 组合订单、明细、支付单等事实，表示整个聚合是否处于已订购阶段。
- `paying` Directory 声明依赖哪些 Information，执行哪个 Action，并通过 Change 物化新事实。
- 支付结果 Directory 声明 success/error 的分类条件。

HTML 展示这些定义，Java 的 `OrderInformation` 和 `OrderPaymentFlow` 提供只读导航，Runtime 负责求值和执行。Store 不再维护另一套“状态值 → Directory”的判断，Workflow 不再抄写 success/error 分支规则。

这种去重并不取消实现代码。数据库访问、锁、类型转换、第三方调用和错误映射仍需要明确的工程实现；去掉的是重复定义业务含义的代码。

## 3. 设计事实与工程机制分离

| 内容 | 归属 | 示例 |
| --- | --- | --- |
| 业务模型及关系 | DEC 设计 | 订单、明细、用户、支付信息 |
| 事实识别与变化 | DEC 设计 | 哪些条件代表支付成功；进入阶段应改变哪些属性 |
| 流程与外部能力选择 | DEC 设计 | Action、case、Back、逻辑 DataSource |
| 传输契约 | DEC 设计 | HTTP method、URL、参数、响应、字段约束 |
| 数据库与第三方集成 | 应用适配 | JDBC、支付 SDK、短信平台、部署表名映射 |
| Java 文件布局 | 生成配置/项目约定 | API 分组、包名、Store 的装配方式 |
| 执行正确性证据 | 测试与 Binding | Design ID → 符号 → 用例 → 本次运行报告 |

例如，Controller 默认按 `System + URL 主资源` 分组，适合当前 Demo。但大型项目可以通过独立生成配置按子资源或业务能力分组，不必修改业务设计以迁就 Java 文件名。

同样，Store 由 Factory 创建是 Demo 的装配选择；真正的语义要求是明确资源与事务生命周期，不能靠每次新建 Store 或空 `commit()` 冒充事务。

## 4. 信息树与流程图各自回答什么

Information 回答“现在是否成立”。它可以基于模型表达式、RuleView 或其他 Information 组合，形成依赖图。信息依赖箭头表示“依赖者指向被依赖者”，并不表示业务执行顺序。

Directory 回答“从哪里、满足什么条件、执行哪些动作后，可以推进到哪里”。它引用 Information，而不是重新定义这些条件。流程中的 Produce、Change、case 和 Back 都有独立语义。

由此可以在同一设计上做两类操作：

1. **命令执行**：执行 Action，产生或改变事实，再识别和验证状态。
2. **业务查询**：选择设计中的阶段范围，读取持久化模型，识别当前事实，不执行流程动作。

业务查询中的“已订购到支付成功”是图上的阶段范围。它不能仅凭当前状态证明订单历史上曾经历哪些阶段；历史查询需要另外设计并持久化事件或业务轨迹。

## 5. YAML 是权威源，XML 是受控交换格式

默认从 YAML 生成 XML 与 HTML。用户或外部系统也可能修改 XML；项目提供同步工具，把 XML 可表达的变更合并回已有 YAML，保留稳定 ID 和 YAML 独有元数据。之后仍从 YAML 重新生成其他产物。

这是一条受控回写路径，不是 XML/YAML 双主实时同步。HTML 是审阅视图，没有回写入口。详见 [三种产物的关系](yaml-xml-html.md) 和 [XML 同步指南](xml-to-yaml-sync.md)。

## 6. 可信度来自可核对的证据

每个需要实现、测试或审阅的设计节点使用稳定 Design ID。生成代码保留 ID 和 YAML/XML 定位，索引帮助人阅读，Binding 连接手写实现、Runtime 能力与测试。

验证分层进行：设计校验 → 解析/编译 → 生成漂移检查 → 真实行为测试 → 符号和测试证据校验。出现未知引用、无法支持的语义、缺失适配器或不明确的分类时，应明确失败或登记 `DESIGN_GAP`，不能用假成功填补缺口。

这也解释了为什么 `PLANNED` 可以被完整登记，却不能被算作实现完成；为什么内存适配器测试不能替代真实 MySQL 验证；以及为什么日志短信不能算作可靠投递。
