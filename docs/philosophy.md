# 项目理念：让设计成为可执行的业务契约

[返回文档总览](README.md)

## 1. 要解决的问题

同一条业务规则常被分别写进需求文档、流程图、接口、代码和测试。例如“订单具备支付条件”，可能在文档中是一段描述，在代码中是一组判断，在查询中又是一份状态列表。规则改变后，维护者需要找出并同步所有副本；遗漏往往要到运行时才会暴露。

在“文档说明意图、代码独立实现”的方式中，两者的一致性主要依赖人的理解和持续核对。DEC 希望让可结构化的业务设计直接参与执行与验证：先明确事实、规则和流程，再让展示、生成代码与运行时共同消费这份定义。这样，一次业务变化有明确的修改起点，也有可检查的影响范围。

理解这份设计，只需先掌握五组概念：

| 核心概念 | 回答的业务问题 | 简单例子 |
| --- | --- | --- |
| Data / View | 数据是什么，业务需要把哪些数据放在一起看？ | 订单及其明细、用户和支付信息 |
| Information | 某个业务事实现在是否成立？ | 订单是否具备支付条件 |
| RuleView | 如何判断条件或执行一组规则？ | 校验支付条件、读取或更新相关数据 |
| Directory | 满足什么条件、经过什么动作，流程才能推进？ | 从已订购进入支付中，再按结果分支 |
| API | 对外提供什么操作，输入和输出有什么约束？ | 提交订单需要哪些字段，返回什么结果 |

这些概念的正式设计以 canonical DEC YAML 保存；canonical 表示它是业务定义的权威版本。Runtime 是消费这些定义的共享执行引擎。“文档即编码”指结构化设计参与程序执行和验证，能力范围仍受模型、执行引擎和实际集成约束，不能把任意自然语言说明直接当作可运行程序。

## 2. 核心理念：设计是协作双方的可执行契约

契约连接**设计侧**与**实现侧**。设计侧负责明确业务意图，实现侧负责把这些意图落实为可验证的行为。两侧都可以由人或 Agent 承担；同一个人也可以先设计、再实现。共同的契约让接手者无需从零散说明和实现细节中猜测业务含义。

设计侧承诺提供可校验的模型、规则、流程和对外约束，为需要追踪的节点提供稳定 Design ID，并明确缺口与变更。稳定 ID 标识同一个设计节点，语义变化仍须显式说明和审阅，不能借改名或改写描述悄悄改变约定。

实现侧承诺按已确认的设计实现行为，明确外部能力与事务边界，并把节点关联到真实实现或运行时能力及测试。这份关联称为 Implementation Binding。实现者可以选择适合项目的工程组织方式，但不能静默省略规则、另写一套业务含义，或把尚未接通的能力标成完成。

契约之所以“可执行”，是因为它约定的部分内容能被程序校验、编译、执行，并与实现证据核对。自动化承担可判定的一致性检查；业务意图是否正确、外部能力是否足够、验收场景是否充分，仍需要人的判断。设计发生变化后，双方都要重新核对受影响的实现和证据。

## 3. 五条核心原则

**原则一：每项业务事实只有一个权威定义。**

canonical YAML 负责定义业务含义，其他产物应能追溯到它。外部 XML 变更通过受控回写进入这份设计，不建立 YAML/XML 双主。产物关系见 [YAML、XML 与 HTML](yaml-xml-html.md)，回写边界见 [XML 同步指南](xml-to-yaml-sync.md)。

**原则二：多个表现形式应由同一事实派生。**

审阅页面、生成的设计导航和运行时计划可以呈现同一条规则，但不应成为各自独立维护的规则副本。修改业务事实后，重新派生并检查一致性；手写实现复用已有业务判断。各层如何消费设计，见 [整体架构](architecture.md)。

**原则三：业务语义由设计约定，工程机制由实现承担。**

“何时允许支付”和“支付失败后可以怎样推进”属于业务语义；如何访问数据库、调用外部服务、管理事务和组织代码属于工程机制。实现选择必须满足契约，不能为了文件布局或技术便利改写业务含义。语义要求与工程约定的区别见 [Skill 使用与维护](skills.md)。

**原则四：关键语义无法确定时，明确报告缺口。**

未知引用、不支持的规则、缺失适配器或无法确定的流程分类，应阻止相应操作被当作成功，或明确登记待解决的设计缺口。这是 fail closed：不给不确定的执行结果贴上成功标签。它要求区分“条件不成立”“信息不足”和“执行错误”，具体边界见 [Java 框架详解](java-framework.md)。

**原则五：完成声明必须有与当前版本相符的证据。**

有设计、有代码、能够编译和行为已验证，是不同层次的事实。Design ID 与 Binding 让实现和测试可追踪，真实场景验证其行为；未实现节点应保留未完成状态。摘要核对能发现漂移，不能证明报告来源或断言充分。验证方式及其保证范围见 [开发与验证手册](development-and-verification.md)。

## 4. 一个贯穿示例：订单支付

假设一个订单流程需要判断是否允许支付，并根据支付结果进入不同阶段。同一业务事实可以有以下表现形式；表中是概念说明，精确条件由实际业务设计决定。

| 同一业务事实 | 在 YAML 中 | 在 HTML 中 | 在 Java 中 | 在运行时 |
| --- | --- | --- | --- | --- |
| 订单是否具备支付条件 | 定义 Information 及其条件或规则引用 | 展示条件与依赖关系，供人审阅 | 生成可追踪的设计引用，供应用接入 | 对当前业务数据求值，决定条件是否成立 |
| 收到支付结果后如何推进 | 声明 Directory 的分类条件及后续动作 | 展示分支与对应规则 | 提供流程设计导航，接入实际外部能力 | 识别结果、选择分支、执行并验证变化 |

如果支付条件发生变化，设计侧修改权威定义，实现侧检查能力是否仍然满足、重新生成受影响产物并验证场景。不同入口引用同一条件，减少各自在代码中解释“可支付”的机会。

数据库访问、并发控制和支付平台调用仍需工程实现。设计集中定义业务含义，使这些实现可以围绕同一份约定协作；它不会自动补全未声明的外部集成。具体类、装配方式与调用链见 [订单支付示例详解](order-payment-demo.md)。

## 5. 信息树与流程图各回答什么

**Information 回答“现在是否成立”。** 它可以读取模型、引用 RuleView，或组合其他 Information，形成信息依赖图。图中的依赖关系表达一个判断需要哪些事实，不代表动作执行的先后顺序。

**Directory 回答“怎样推进”。** 它引用已定义的事实，约定推进条件及动作。Action 表示要执行的动作，Produce 描述动作的产出及相关事实要求，Change 声明要物化的目标事实，case 按条件选择结果分支，Back 描述允许的回退动作与目标。详细语义见 [设计模型](design-model.md)。

命令和查询因此可以使用同一套业务含义：命令执行动作、改变事实并验证结果；业务查询读取数据、识别当前事实，不执行流程动作。

这套模型必须区分**当前成立**与**历史上曾经成立**。例如查询“已订购到支付成功”，表达的是流程图上的阶段范围，不能据此证明某订单曾依次走过全部阶段。回退后，当前事实可能已不再包含之前的支付结果；Back 也不能撤销已经发生的历史或自动收回外部副作用。需要审计、历史查询或重放时，必须另行设计并持久化事件或业务轨迹，不能从当前模型推断出不存在的历史证据。

## 6. 代价与适用边界

采用 DEC 需要前期投入。团队要学习区分数据、事实、规则和流程，把原本藏在代码或沟通中的约定明确表达出来。建模、稳定身份维护、适配器接入和证据更新都会增加初期成本；模型是否清楚，仍取决于设计者对业务的理解。

执行和生成也有约束。应用依赖 Runtime 的语义与能力，需要维护它与设计版本的兼容性；生成器只覆盖已支持的结构和表达形式。遇到缺失能力，可能需要扩展模型、框架或适配器，并承担相应验证成本。支付、消息、数据库之间的一致性，以及可靠投递、补偿和历史追踪，都需要明确设计，不能由一张流程图自动保证。

当业务规则需要被多个入口复用、系统生命周期较长、交接频繁，或人和 Agent 持续协作时，减少语义副本与提供可追踪契约的收益更容易累积。采用前可以问：同一规则是否已在多处重复？变化是否经常造成不一致？这些问题是否值得长期投入来治理？

对于生命周期短、规则少且变化快的一次性项目，建模和工具维护成本可能超过收益。业务尚在探索时，也应先确认哪些语义值得稳定下来，再决定建模范围。DEC 适合承载能够明确表达并反复验证的业务契约，不要求把项目所有代码都变成设计声明。
